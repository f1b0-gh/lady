## Scope and sources of truth

The matrix describes `profiles/podman-vm.ncl` and `profiles/podman-debug.ncl`,
which share the same policy. The addresses below belong to the documentation
range and are used only by the isolated QEMU fixture. Configure site addresses,
server identities and certificate trust explicitly before deployment.

The current rules are generated by `nix/network.nix`; profile validation is in
`profiles/schema.ncl`, `nix/profile.nix` and `src/profile.rs`. The resolved plan
and delivered `/etc/nftables.conf` record the selected policy. This document is
a review aid, not a replacement for those inputs or evidence of a successful
runtime test. DHCP-only and offline profiles have different contracts.

Interface: `enp0s2`. Input, output and forwarding default to drop. No SSH server,
Podman API socket, workload or automatic image update is enabled by these images.
A permitted destination or published port does not create a listener or workload.

## Site flows

Ports below are destination ports unless a source port is specified. Replies
normally use the stateful return rule in the next table.

| ID | Initiator / direction | Destination or allowed source | Protocol / ports | Current NTS image | Purpose |
| --- | --- | --- | --- | --- | --- |
| F01 | Host DHCP client, output | DHCP server or broadcast on `enp0s2` | UDP source 68 -> destination 67 | Allowed | Address discovery and renewal |
| F02 | DHCP server, input | Host on `enp0s2`; source IP is not pinned | UDP source 67 -> destination 68 | Allowed | DHCP lease replies; this is not server authentication |
| F03 | Host / rootless container traffic, output | DNS resolver `192.0.2.1` | UDP and TCP 53 | Allowed | Explicit DNS, including TCP responses; no fallback resolver |
| F04 | Host time client, output | Time endpoint `192.0.2.1` | UDP 123 | NTS-authenticated NTP only in the time client | Clock synchronization; the packet filter cannot distinguish NTS authentication |
| F05 | Host time client, output | Declared NTS-KE endpoint; lab `192.0.2.1` | TCP 4460 | Allowed; isolated runtime test passed | TLS key establishment, certificate and server identity verification |
| F06 | Host / rootless container traffic, output | Explicit HTTPS endpoint `192.0.2.2` | TCP 443 | Allowed | Declared registry/application HTTPS; not unrestricted Internet access |
| F07 | Declared remote client, input | Source `192.0.2.3` to the host | TCP 8080 | Allowed | Optional explicitly published workload port; no default listener |
| F08 | Any other new remote traffic | Any other destination, source or port | Any | Dropped | Deny traffic not declared by the profile |

The site rules match addresses, protocols and ports, not process identities.
Their purpose labels do not imply per-service or per-container authorization.
The profile also refuses generic egress entries that would reopen UDP/123 or
TCP/4460 toward an address outside the declared NTS list; the protocol/port pair
is significant (TCP/123 and UDP/4460 are separate application flows).
Rootless pasta opens host sockets, so its external traffic traverses host
input/output policy; a dropped forwarding chain alone is not container egress
isolation. A workload requiring further destinations needs an explicit profile
change and review.

## Common state and control traffic

| ID | Scope | Current rule | Consequence |
| --- | --- | --- | --- |
| C01 | Loopback input/output | Accepted before remote filters | Includes the local DNS stub and local IPC over IP; not a remote permission |
| C02 | Non-loopback IPv6 | Dropped; IPv6 is also disabled by sysctl | No IPv6 alternative to the declared IPv4 policy |
| C03 | Invalid connection-tracking state | Dropped | No invalid-state exception for a declared endpoint |
| C04 | Established/related input/output | Accepted before site rules | Existing authorized sessions and related replies can continue after a rule is removed; revocation tests must use new connections |
| C05 | ICMPv4 errors, input/output | Destination-unreachable, time-exceeded and parameter-problem accepted | Error reporting, including path-MTU errors; this rule is not restricted to the site peer addresses/interface |
| C06 | Other ICMPv4, including new echo requests | No explicit permission | Dropped unless separately covered by an existing connection state |
| C07 | Kernel forwarding | Dropped; IPv4 forwarding disabled | No routed gateway role |
| C08 | ntpd-rs to local kernel | AF_NETLINK for NETLINK_ROUTE interface notifications | No remote port; CAP_NET_ADMIN is absent, so network administration remains forbidden |

DHCP-provided DNS, time servers and hostnames are ignored. IPv6 router
advertisements, link-local addressing, LLDP, LLMNR and mDNS are disabled.
DNS transport is not authenticated by this matrix. NTS must independently
validate the time server identity even when DNS is used to resolve its name.

## Required NTS behavior

- Use ntpd-rs; timesyncd is compiled out and its unit masked. Configure only authenticated
  sources, with no plain-NTP source, pool, DHCP source or automatic fallback.
- Trust only the configured bundle; the service unsets `SSL_CERT_DIR`, so PEMs
  retained separately under `/etc/ssl/certs` do not extend trust implicitly.
- Verify the certificate chain, expected server identity and certificate
  validity period. A first boot therefore needs a sufficiently accurate RTC or
  another explicitly trusted initial clock; do not bypass certificate time checks.
- Keep NTS-KE and NTP destination addresses/ports explicitly bounded. A negotiated
  NTP endpoint outside that policy must fail. The native client also checks the
  exact expected IP:123 per source, because unrelated DNS grants can overlap; do not open dynamic destinations
  merely because a server or DNS response advertises them.
- NTS-KE establishes keys over TLS; time packets continue over UDP with NTS
  authentication. Existing valid cookies may allow authenticated synchronization
  during an NTS-KE outage. That is not an unauthenticated fallback.
- A failed exchange leaves the client unsynchronized. It must not report a
  successful authenticated synchronization or silently trust ordinary NTP.
  This requirement does not itself gate workload startup on synchronized time.

## Qualification and maintenance

`tests/network_vm.py` connects two disposable guests by an inherited AF_UNIX
socketpair, without Internet access. Its peer and control endpoints are test
fixtures, not additional production services. `tests/network_guest.py` and
`tests/network_fixture.py` exercise DHCP, explicit DNS/time sources, host and
rootless traffic, ingress source filtering, atomic firewall replacement and
outages. The concise current results and their limits live in the original local
`nickeling/docs/bootc-podman/2026-11-15` report, which is not bundled here.
The maintained drivers and fixtures remain available for new qualification.

Passed isolated real NTS qualification covers: a valid authenticated exchange, untrusted CA,
wrong server identity, expired/not-yet-valid certificate, unauthenticated NTP
responses, NTS-KE outage with fresh state, valid cached-cookie behavior, and a
negotiated endpoint outside the allowlist. A reachable UDP/123 service alone
is never evidence of NTS success. Both guests exited successfully; eleven NTS
observations and peer counters are retained in `nts-runtime-current.json` in
that historical report. This does not qualify deployment infrastructure.
Never disable certificate checks for the fixture.

When the profile changes, update its Nickel/JSON forms, all validators, the
resolved inventory, firewall and client configuration, this matrix and relevant
tests together. Rebuild minimal/debug, measure their sizes and regenerate their
Ladybom SBOMs against the new exact archive digests. Preserve the unchanged
source, recipe and concise report; clean completed disposable VM outputs.
